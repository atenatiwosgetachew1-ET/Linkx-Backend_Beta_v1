# Handoff: Edge Semantic Metadata — Graph Visualization Accuracy

## Problem Statement
The xVigilance anomaly detection engine creates Neo4j relationship edges between transaction nodes. Previously, **all edges were rendered as directional solid arrows**, regardless of what the anomaly rule actually proved. This caused investigators to misinterpret analytical groupings (e.g., "these transactions share the same hub account") as actual money transfers (e.g., "Transaction A sent money to Transaction B").

## What Changed (Backend — Already Deployed)
Every anomaly rule in `xvigilance_consumer.py` now writes **three new metadata properties** onto every relationship edge:

| Property | Type | Description |
|---|---|---|
| `edge_semantic` | `string` | What kind of relationship this edge represents |
| `financial_flow` | `boolean` | Whether this edge represents actual observed money movement |
| `directed_display` | `boolean` | Whether the frontend should render an arrowhead |

### Values by Anomaly Rule

| Rule | `edge_semantic` | `financial_flow` | `directed_display` | What the edge actually means |
|---|---|---|---|---|
| `SMURFING` | `TEMPORAL_SEQUENCE` | `false` | `true` | Same sender→beneficiary pair, ordered by time. Arrow = "happened before" |
| `CIRCULAR_FLOW` | `OBSERVED_FLOW` | `true` | `true` | Actual reverse transfer pair (A→B and B→A). Arrow = real money direction |
| `FUND_FLOW` | `TEMPORAL_SEQUENCE` | `false` | `true` | Beneficiary of Txn A later acts as sender in Txn B. Arrow = time order |
| `DORMANT_TO_ACTIVE` | `NODE_FLAG` | `false` | `false` | Self-loop flag on a single transaction (dormant source → active beneficiary) |
| `ABNORMAL_BALANCE_CHANGE` | `TEMPORAL_SEQUENCE` | `false` | `true` | Consecutive txns on same account with abnormal balance swing. Arrow = time order |
| `HUB_AND_SPOKE` | `GROUPING` | `false` | `false` | Transactions share a common hub account. **No money flow between these nodes** |
| `SHARED_IDENTIFIER` | `GROUPING` | `false` | `false` | Transactions share a phone number across different accounts. **No money flow** |

## What the Frontend Must Implement

### Edge Rendering Rules

Read the `edge_semantic`, `financial_flow`, and `directed_display` properties from every edge in the graph data. Apply the following visual rules:

#### 1. `financial_flow == true` AND `directed_display == true`
**Render:** Solid arrow (current default behavior)
**Use case:** `CIRCULAR_FLOW` — the only rule where the arrow represents actual money movement.
```
───────────────►
  solid line + arrowhead
```

#### 2. `financial_flow == false` AND `directed_display == true`
**Render:** Dotted/dashed arrow with a distinct color or opacity reduction
**Use case:** `SMURFING`, `FUND_FLOW`, `ABNORMAL_BALANCE_CHANGE` — the arrow means "happened before in time", not "sent money to".
```
· · · · · · · · ►
  dotted line + arrowhead
```
**Tooltip text:** "Temporal sequence — arrow shows time order, not money flow"

#### 3. `financial_flow == false` AND `directed_display == false`
**Render:** Dashed line with **no arrowhead** (undirected)
**Use case:** `HUB_AND_SPOKE`, `SHARED_IDENTIFIER` — these edges only mean "these transactions are grouped by a shared property".
```
- - - - - - - - -
  dashed line, no arrowhead
```
**Tooltip text:** "Analytical grouping — shared hub account [hub_account] / shared identifier [identifier_value]"

#### 4. `edge_semantic == 'NODE_FLAG'`
**Render:** Self-loop badge or icon on the node itself (e.g., a warning icon overlay)
**Use case:** `DORMANT_TO_ACTIVE` — this is a property of a single transaction, not a relationship between two.

### Backward Compatibility
If `edge_semantic` is missing (older data before this update), fall back to the current default behavior (solid directional arrow).

### Legend / Key
Add a small legend to the graph window explaining the three edge styles:
- **Solid arrow** → Observed financial transfer
- **Dotted arrow** → Time-ordered sequence (not a transfer)
- **Dashed line** → Analytical grouping (shared property)

## Example Edge JSON from API

```json
{
  "from": "95c50b42-...",
  "to": "b013f6d5-...",
  "label": "HUB_AND_SPOKE",
  "bgcolor": "#6f42c1",
  "reason": "account connects with multiple counterparties on same day",
  "hub_account": "2491811",
  "direction": "incoming",
  "spoke_count": 1833,
  "edge_semantic": "GROUPING",
  "financial_flow": false,
  "directed_display": false
}
```

For this edge, the frontend should render a **dashed line with no arrowhead**, because `financial_flow` is `false` and `directed_display` is `false`.

## No Backend Changes Required
The edge metadata is already being generated by the xVigilance worker and automatically flows through the existing `promote_anomalies_to_postgres` pipeline into the API responses. The frontend only needs to read the new properties and adjust its rendering logic accordingly.
